# ADR-0017：派生练习版本使用独立修订链支持继续修改与撤销

日期：2026-08-13  
状态：已接受

## 决策

每个 `PracticeVersion` 保留由白名单 `EditPlan` 生成的基础 MusicXML，并新增完全独立于主谱 `ScoreRevision` 的 `PracticeVersionRevision` 修订链。派生版本上的人工校正遵循与主谱相同的安全边界：

- 只允许当前确定性编译器支持的音高、时值、音符/休止符和相邻同音延音线操作；
- 每次操作先解析、校验并写入新的 MusicXML 文件，再在单个 Room 事务中插入修订并切换该派生版本的当前指针；
- 撤销、重做和历史切换只移动派生版本自己的指针，不删除历史文件；
- 主结构的 `currentRevisionId`、原始 OMR 修订和其他派生版本始终不变；
- 导出、试听、指导和 MIDI 跟弹读取派生版本当前修订，而不是固定读取最初候选文件。

`PracticeVersion.currentRevisionId` 为空时表示仍处于算法生成的基础候选；非空时必须引用同一版本的有效 `PracticeVersionRevision`。基础候选仍保留在 `PracticeVersion.musicXmlRelativePath`，作为派生修订链的稳定恢复点。

## 数据、迁移与备份

- Room 从 v10 升级到 v11：`practice_versions` 新增可空 `currentRevisionId`，新增 `practice_version_revisions` 表。
- `.gpiano` 从 v5 升级到 v6：加入派生版本当前指针、修订元数据和全部修订 MusicXML；继续读取 v1～v5，旧版本的当前指针默认为空。
- 恢复前必须验证修订的版本归属、父子关系、修订号、相对路径、MusicXML 结构以及每个当前指针；任一不一致在写入前拒绝整个备份。
- 恢复顺序为主谱与修订、派生版本、派生版本修订、跟弹记录和 MIDI 事件。

## 原因

算法候选的“采纳/拒绝”不能替代学习者自己的判断。学习者需要在不破坏主谱的前提下修正候选中的音高、节奏或连线，并能撤销不满意的修改。复用主谱修订表会污染主谱历史和当前指针语义，因此派生版本必须拥有独立修订链。

## 后果与边界

- 首版支持整项候选采纳/拒绝，以及候选内部的确定性人工校正与撤销；尚不提供制谱软件级自由排版或任意 AI 操作。
- 原始算法差异继续描述“主谱 → 基础候选”的取舍；派生修订历史单独描述用户在候选上的后续校正，二者不可混写。
- 后续如果支持逐条接受 AI 操作，应扩展受约束 `EditPlan`，而不是绕过本修订链直接改写 MusicXML。
