# Gpiano AI：长期项目上下文

最后更新：2026-08-12

## 现在是什么

Gpiano AI 是面向钢琴学习者的本地优先 Android 练习伙伴。它希望把学习者自有或已获授权的静态琴谱，转化为可渲染、可播放、可理解、可编辑并可与真实演奏对齐的个人练习材料。

```text
授权谱面 → OMR → MusicXML / ScoreIR → 结构化谱面工作区
                                      ├→ 片段播放与谱面解释
                                      ├→ 可编辑的派生练习版本
                                      └→ MIDI 跟弹与基础匹配反馈
```

直接用户是处于不同练琴阶段的钢琴学习者。教师或专业人员可以参与内容和方案校验，但当前不建设独立教师端、琴行端或机构工作流。

## 已确定决策

- 本地优先、无账号；原始谱面和演奏数据默认不上传。模型调用或数据传输须明确授权并最小化。
- MusicXML 4.0 是用户可带走的记谱主交换格式；MIDI 文件与消息用于播放、设备通信和演奏事件。
- 原谱、OMR 草稿、用户/AI 修订版并存；低置信度结果不能伪装为确定乐谱。
- 内部 `ScoreIR` 负责稳定标识、编辑、校验、播放和版本关系，但不得成为无法导出的私有孤岛。
- AI 返回受约束、可校验的编辑计划，不直接覆盖原谱；建议必须可预览、修改、撤销和拒绝。
- MIDI 首期只做边界清晰片段的音高、节奏、漏音、多音和连续性反馈，不扩展为全面演奏评分。
- 现有 Kotlin、Jetpack Compose、Room、Storage Access Framework 和 PdfRenderer 作为 Android 基础；DataStore 属于偏好持久化的计划能力，OMR、刻谱、播放、AI 和 MIDI 通过接口隔离。

## 当前实现事实

### 本地琴谱底座

- 已实现 PDF、JPG、PNG、WebP 和图片组导入，文件复制到 App 私有目录。
- 已实现曲谱搜索、重命名、收藏、文件夹创建与归属、书签、页面顺序和删除。
- 阅读器按可视尺寸渲染 PDF/图片并预取下一页；支持翻页、隐藏控件和基础节拍器。
- Room 数据库当前版本为 6，已有 `Score`、`ScorePage`、`Bookmark`、`Folder` 及 1→6 迁移。
- `.gpiano` 当前只导出/恢复曲谱基础元数据、收藏状态和原始文件；尚未覆盖文件夹、书签、页面顺序、阅读状态或未来结构化练习数据，不能称为完整备份。

### 结构化乐谱 Debug Spike

- 底部导航已有“练习工作区”入口；当前数据来自 `test-res/1785910774247300_654.musicxml`，不是 OMR 输出。
- `MusicXmlSource` 隔离数据来源，`AssetMusicXmlSource` 是当前 Debug 实现；未来 OMR 适配器应实现同一入口。
- `MusicXmlInspector` 可读取标题、声部、小节数、调号和拍号摘要，并按出现顺序建立稳定页面小节索引。
- alphaTab 1.6.1 已在 Android 设备渲染测试 MusicXML 的双谱表、和弦、调号、拍号、三连音和连线。
- 工作区采用紧凑布局；顶部小节选择依据 alphaTab 主小节边界滚动到对应谱面位置，第 2、3 小节已完成设备复测。
- alphaTab Android 通用 `load` 入口存在类型分支问题；当前通过隔离的 `ScoreLoader`→`renderScore` 适配加载原始 MusicXML。

### 尚未实现

- OMR、识别置信度、原谱与 MusicXML 的位置映射。
- 正式 `ScoreIR`、稳定音符标识、音符/时值校正、MusicXML 重生成、修订持久化与撤销。
- 选段播放、慢速、循环、左右手筛选、谱面高亮和 AI 解释。
- 派生练习版本、差异预览、AI 改编、MIDI 设备接入和演奏匹配。
- 结构化乐谱相关 Room 模型、迁移及 `.gpiano` 完整备份。
- 自动化单元测试、仪器测试和发布版本的结构化工作区入口。

## 当前工程顺序

1. 在新增持久化前补齐 `ScoreStructure`、`ScoreRevision`、位置映射和备份迁移 ADR/设计。
2. 基于测试 MusicXML 建立最小 `ScoreIR`、稳定小节/音符标识和渲染映射。
3. 完成一次“选择音符 → 修改音高或时值 → 校验 → 重生成 MusicXML → 重渲染 → 保存修订版”的可验证闭环。
4. 基于同一结构实现选段、播放时间轴、慢速/循环/分手和高亮。
5. 工作区闭环稳定后，通过已有数据接口接入单页 OMR、置信度与原谱位置映射。
6. 再推进 AI 解释/可编辑改编与 MIDI 跟弹，避免各自建立不兼容的位置和时间模型。

## 第二周交付差距

第二周对外交付要求是可体验的“单页琴谱转换 → 结构化草稿 → 人工校正”。当前只完成其下游的 MusicXML 展示与小节定位，尚未完成 OMR、人工校正和结果保存，因此不能将本周核心版本标记为完成。

已有一条真实界面反馈：谱面有效显示区域过少、小节选择缺乏明显作用。已据此压缩辅助区域并让小节选择滚动定位。完整流程仍需至少两位目标学习者体验；现阶段没有可提交的完整用户验证结论。

## 当前风险与约束

- alphaTab 适配使用反射构造 `Uint8Array`，升级依赖前必须补回归测试或替换为稳定公开入口。
- “练习工作区”代码位于主源码，但测试 MusicXML 只打入 Debug assets；发布前须隐藏入口或接入正式数据源。
- 备份恢复当前不是事务式完整恢复，不能让新结构化数据直接接入现有备份实现。
- 测试样本的授权状态须在作为比赛证据或发布资源前确认；私人曲谱和截图不得进入仓库。
- 当前没有自动化测试，设备演示通过不等于数据迁移、恢复和编辑正确性已经受保障。

## 不要做

- 不建设在线曲谱库、账号体系、独立教师端或默认云同步。
- 不用手工假谱、静态占位或临时渲染结果替代真实 MusicXML 工作区。
- 不以黑盒方式覆盖原谱，不把 AI 建议或单次 MIDI 匹配包装为唯一正确答案。
- 不在未校正或低置信度结构化乐谱上输出确定性改编或演奏反馈。
- 不提交私人琴谱、演奏记录、密钥、证书、构建目录或 `local.properties`。
