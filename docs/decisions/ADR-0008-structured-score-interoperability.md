# ADR-0008：结构化乐谱采用标准交换格式与可替换渲染架构

日期：2026-08-11  
状态：已接受

> 进展说明（2026-08-12）：刻谱实现的 Debug 选择已由 ADR-0009 落到 alphaTab；编辑数据仍以 MusicXML/ScoreIR 为边界，播放能力尚未完成验证。本说明不改变本 ADR 的格式互操作性决策。

## 决策

1. 将 MusicXML 4.0（`.musicxml` / `.mxl`）作为用户可编辑乐谱的主交换格式；将 Standard MIDI File（`.mid`）和标准 MIDI 事件作为播放、设备与演奏记录的交换格式。
2. 原始谱面、OMR 原始输出、规范化结构化乐谱和用户/AI 修订版并存保存；原始文件与 OMR 输出不得被覆盖。
3. 使用内部 `ScoreIR` 支撑编辑、校验、AI `EditPlan`、播放和版本管理，但必须能够导入、导出标准 MusicXML/MIDI。
4. 渲染器、合成器和 OMR 服务均通过接口隔离，不将其私有格式作为用户数据。alphaTab 与 OSMD/独立播放链路的选择须以测试 XML 技术 Spike 结果决定。

## 原因

- 用户需要在 Gpiano 外继续使用编辑后的乐谱和练习结果，不能被某个 App 或渲染库锁定。
- MusicXML 保留记谱结构，适合编辑、AI 分析和重新渲染；MIDI 适合播放、电钢琴通信和演奏事件。
- OMR 结果不可靠，原谱、草稿和修订版并存才可追溯、可撤销，也便于逐步改善识别与校正体验。
- 渲染后视觉排版不需复刻输入图片；结构化音乐语义和用户可控的编辑结果才是产品资产。

## 后果

- 实现前需定义 `ScoreIR`、`ScoreRevision`、`CorrectionOperation`、`PlaybackPlan` 及其备份迁移规则。
- MusicXML 导入需要处理不规范或不完整的 OMR 输出，例如双 `part` 钢琴谱、重复的小节号、多声部和缺失方向信息。
- 须在每次导出前完成结构与格式校验；高级记号跨软件显示差异需如实提示。
- 需完成 alphaTab 技术 Spike，再决定具体渲染与播放依赖，并补充依赖选型 ADR。
